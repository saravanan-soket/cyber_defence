  Plan: from ExploitBench to a CVE patch-trace factory

  Goal: for every CVE with source code, an agent finds the bug, writes a patch,
  and writes a regression test. A verifier checks the result. Every step of the
  agent's reasoning goes to Langfuse with a quality label, so the traces can be
  used to train a model on patching.

  1. Should we keep the grader?

  Keep it, but turn it into a verifier that labels trajectories instead of
  scoring a leaderboard. Training on unchecked patches teaches the model to
  write plausible-looking patches that are wrong. The verifier adds no LLM
  judge; it only runs tests and attaches a label. Low-quality traces stay in
  Langfuse, and you filter by label when you build a training set.

  2. One agent workflow for every CVE

  CVE record → fetch source at the vulnerable version
    1 SETUP     agent gets the project building and its tests running (network
  allowed);
                snapshot the image. The 7 language builders we have become fast
  paths/hints.
    2 LOCATE    agent reads the CVE text and the code to find the root cause
    3 REPRODUCE agent writes a regression test that FAILS on the vulnerable code
    4 PATCH     agent writes a minimal fix
    5 VERIFY    agent runs its test (now passes) plus the existing tests (still
  pass)
    6 SUBMIT    patch + test + root-cause report
  → independent verifier (offline, fresh container) → label → Langfuse score

  The agent never sees the upstream fix commit. If it did, the trace would just
  be "copy the diff", which is useless for training. The upstream fix stays
  hidden and is used only to check the agent's work.

  3. Quality tiers (the label on each trace)

  Tier: T1 gold
  When: upstream fix includes a test
  Verifier checks: upstream test fails on the vulnerable code and passes on the
  agent's patch; existing tests pass
  Est. pool: ~4k
  ────────────────────────────────────────
  Tier: T2 strong
  When: upstream fix exists, no test
  Verifier checks: agent's test fails on the vulnerable code and passes on both
  the agent's patch and the upstream fix; existing tests pass
  Est. pool: ~40k
  ────────────────────────────────────────
  Tier: T3 medium
  When: no fix commit, but the CVE lists a fixed version
  Verifier checks: agent's test fails on the vulnerable version, passes on the
  patch, and passes on the fixed release tag
  Est. pool: ~30k+
  ────────────────────────────────────────
  Tier: T4 weak
  When: no fix, no fixed version
  Verifier checks: agent's test fails before the patch and passes after;
  existing
  tests pass (self-consistent only)
  Est. pool: rest
  ────────────────────────────────────────
  Tier: rejected
  When: test doesn't fail first, patch breaks tests, build fails
  Verifier checks: the trace is kept but labelled rejected
  Est. pool: —

  The cross-checks in T2 and T3 (the upstream fix or fixed release must also
  pass the agent's test) are what stop an agent from writing a test that fits
  its own patch and nothing else.

  4. Capturing reasoning in Langfuse

  - The client already reads GLM's reasoning_content (litellm_client.py:529
    (exploitbench/runner/llm/litellm_client.py#L529)). I have not yet confirmed
    that it reaches Langfuse, or that it is sent back to the model on each turn
    so the multi-turn reasoning stays intact; I'll check both on the first run.
  - One trace per CVE attempt. Each model call is a generation that carries its
    reasoning; each tool call and result is a span.
  - Metadata: CVE, CWE, language, repo, commits, tier, and model.
  - Scores: tier, test_fails_before, test_passes_after, existing_pass,
    matches_upstream, plus diff size.
  - Local copy: transcript.jsonl stays the source of truth, because Langfuse can
    drop or sample data.
  - Export: a tool to export traces as SFT/RL JSONL, filtered by tier.

● Good question, and the crash-test idea is exactly the right instinct for the
  no-commit case. Let me go through each category: what blocks it, and what
  "yes" takes. Then the crash-test loop, which is the key to the biggest
  category.

  The crash-test loop (for CVEs with no fix commit)

  Your proposed flow is the standard one, and it's sound:

  vulnerable source → build → write a test that triggers the bug
  (crash/assert/leak)
    → confirm it fails/crashes on the vulnerable code   [must fail here]
    → agent patches
    → re-run the same test → now clean → success

  This works without an upstream fix because the test itself is the oracle. The
  one rule that keeps it honest: the test must fail on the vulnerable code
  first, for the right reason. A patch that passes a test that never failed
  proves nothing. That's already the agent_test_fails_on_vuln check in the
  verifier, so the machinery exists.

  What makes it trustworthy enough to not need a fix commit:
  - A crash is a strong, unambiguous signal. Compile with AddressSanitizer /
    UBSan (C/C++), or -fsanitize equivalents; a memory-safety CVE then crashes
    with a diagnostic on the vulnerable build and is silent on the patched
    build. No human judgement.
  - Where a public reproducer exists, use it instead of inventing one. OSV /
    OSS-Fuzz ship a crashing input for ~3,800 bugs. That's the highest-value,
    most reliable slice — the reproducer is the test, already known to crash.

  The honest limits of this loop, which is why I tier it lower than a fix-commit
  task:
  - An agent-written test can be wrong: it can crash for an unrelated reason, or
    test the agent's own patch rather than the bug. The sanitizer-stack-trace
    check (does the crash sit in the function the CVE names?) catches much of

    fix-commit tasks (T1/T2) stay the gold standard.

  What each "not yet" category needs

  ~62,000 open source, no fix commit — the crash-test loop above
  - Blocking: two things. (1) No builder that checks out the vulnerable version
    from the CVE's affected-version range (a tag or date, not a commit). (2) No
    sanitizer build path.
  - To "yes": resolve the affected version → tag/commit from the advisory; build
    with sanitizers on; let the agent write the reproducer; verify crash-before
    / clean-after. Where a fixed version exists, also run the agent's test
    against it (→ T3). OSS-Fuzz reproducers first — highest yield, ~3,800 bugs.
  - Realistic: most become T4, some T3. Big pool, lower average tier.

  ~52,000 fix commit not on GitHub
  - GitLab / Bitbucket / cgit (~35k): small change. The task builder assumes
    github.com/... URLs; teach it the other hosts' commit-URL and clone formats.
    Mostly a parsing job. These stay T1/T2 (they have a real fix commit).
  - Linux kernel (~17k): genuinely hard and separate. Blocking: a kernel build
    is ~30–60 min and the tests boot a VM (syzbot reproducers under qemu/KVM),
    which this k8s/DinD setup can't do as-is. Needs its own track with KVM
    nodes. High cost per task; I'd leave it last.

  16,337 C/C++ with a GitHub fix
  - Blocking: no C/C++ adapter. Builds are make/cmake/autotools with no standard
    "run one test" command, and many projects have no unit tests.
  - To "yes": a C/C++ adapter that detects the build system and compiles with
    sanitizers, so even projects without a test suite are gradable by
    crash-test. This shares all the sanitizer work with the no-commit category,
    so doing them together is efficient.
  - Realistic: fix-commit C/C++ where the fix adds a test → T1/T2; the rest fall
    back to crash-test → T4.

  253,000 no open-source code — stays no. There's nothing to patch or build.
  This is the real ceiling.

  The order I'd build it

  1. Allow fixes without tests in the 7 current languages (agent writes the
     test, cross-check against the upstream fix → T2). Cheapest win, roughly
     doubles the usable pool, no new infrastructure.
  2. Sanitizer build + crash-test verifier path. Unlocks the no-commit loop and
     C/C++ at once.
  3. OSS-Fuzz ingestion (~3,800 reproducers) — reuses step 2, highest
     reliability.
  4. Non-GitHub hosts — small, keeps tasks at T1/T2.
  5. C/C++ adapter.
  6. Vulnerable-version resolver for the 62k no-commit pool.
  7. Kernel track last — its own KVM infrastructure.

❯ explain me the entire pipeline on how it works

● Here's the whole pipeline, following one CVE from a database record to a
  labelled training example. I'll name the real components as I go.

  The goal in one line

  For a known vulnerability, an LLM agent finds the bug, writes a test that
  proves it, patches it, and re-proves the fix — and a trusted, non-LLM verifier
  labels how convincingly it did so. The agent's full reasoning is kept as
  training data.

  ---

  Stage 0 — Triage and advisories (offline, on the host)

  Two one-time passes over the public corpora:

  - scripts/triage.py reads the CVE list (414k records) and the OSV database,
    and writes one row per CVE to cve_triage.jsonl: does open-source code exist,
    is there a fix commit, is it on GitHub, which language/ecosystem. This is
    the sorting that told us ~11,439 CVEs are reachable today.
  - scripts/extract_advisories.py → advisories.jsonl: for each open-source CVE,
    the description, CWE and affected versions — scrubbed of commit hashes and
    fix links (cvepatch/core/ingestion/advisory.py). This is the text the agent
    is later allowed to read. 142,679 of them exist.

  Nothing is cloned or built here. It's pure metadata.

  ---

  Stage 1 — Task generation (host: clone + read diffs only)

  scripts/taskgen.py samples CVEs per language and calls build_task() in
  cvepatch/core/taskgen/core.py. For each CVE with a GitHub fix commit:

  1. Clone the repo (cached), find the fix commit and its first parent, the
     vulnerable commit.
  2. Diff them. A per-language adapter (cvepatch/core/taskgen/languages.py)
     classifies each changed file as test / source / dependency-manifest, and
     decides the base image, build command, and dependency warm-up.
  3. Write a task bundle (below).

  The adapter is the only language-specific part; everything else is shared.
  Seven adapters exist: Go, Python, JS/TS, Java, Rust, PHP, Ruby.

  A CVE is skipped if the fix touches dependency files (can't grade offline),
  has no source change, or the repo layout isn't understood.

  The bundle — the split that makes it honest

  <task_id>/
    baseline/                  vulnerable source (git archive, no history)   →
  goes in the image
    public/defensive_task.json redacted task the agent may read              →
  goes in the image
    Dockerfile, .dockerignore, env_manifest.yaml, meta.json
    hidden/                    NEVER in the image — mounted only into the
  verifier
      task.json                full task: fix commit, build/test commands
      reference/fix.patch      the upstream code fix (the answer)
      reference/test.patch     the upstream test change
      oracle/                  the fix commit's own tests + run.sh (if any)

  The agent gets a shell in its container, so anything in the image is readable.
  That's why everything that reveals the fix lives in hidden/, excluded by
  .dockerignore and bind-mounted only into the verifier's separate container.
  The public task has the fix commit, file names, test commands and evidence
  URLs stripped; a test checks there's no leak.

  Two kinds of bundle:
  - Oracle bundle — the fix shipped a test. That test becomes the hidden oracle.
  - No-oracle bundle (step 1, just added) — the fix shipped no test. The agent
    must write its own; the hidden upstream fix is kept only for cross-checking.

  ---

  Stage 2 — Confirmation (DinD pod: build + verify the reference)

  scripts/taskgen_confirm.py runs where Docker is available. For each bundle:

  1. Build the task image (dependencies are fetched here, at build time — the
     episode and verifier both run with no network).
  2. Run the production verifier on the upstream fix itself, shaped like an
     agent submission.
  3. Accept the task only if that comes out T1 — i.e. the upstream tests fail on
     the vulnerable code (for a real reason, not a compile error) and pass with
     the fix. Result: REPRODUCIBLE.
     - No-oracle bundles can't be T1-verified, so they instead get a build-only
       check (image builds, fix applies and compiles) → BUILDABLE.

  This filters out broken images, flaky tests, and "fixes" whose test doesn't
  actually catch the bug — before any model time is spent.

  ---

  Stage 3 — The agent episode (GLM-5.3 in the task container)

  cvepatch benchmark (the runner: cvepatch/runner/) starts the task image with
  --network none and connects GLM over MCP. The agent's tools
  (cvepatch/core/mcp_server/tools.py):

  - setup() → the advisory text and the 5-step workflow
  - read_file, list_directory, search_code, inspect_diff — explore
  - write_file, run_command — a real shell in its writable copy of the source
  - apply_patch
  - submit_fix(test_files, test_command) — splits the agent's diff into its test
    and its fix
  - submit_report(...) — the root-cause write-up

  The workflow it's told to follow: locate the bug → reproduce it with a test
  that fails on the vulnerable code → patch the source → verify its test passes
  and existing tests still pass → submit. The upstream fix is never shown.

  Everything — every model turn with its reasoning_content, every tool call and
  result — is written to the run's transcript.jsonl.

  ---

  Stage 4 — Verification and tiers (fresh container, no network, no LLM)

  cvepatch/core/verifier/verify.py runs after the episode in a clean container
  with hidden/ mounted read-only. It replays the agent's submission and runs
  each check twice, requiring the same outcome:

  ┌─────────────────────────────────────┬───────────────────────────────────┐
  │                Check                │              Meaning              │
  ├─────────────────────────────────────┼───────────────────────────────────┤
  │                                     │ the agent's test fails on the     │
  │ agent_test_fails_on_vuln            │ vulnerable code, and not merely   │
  │                                     │ because it won't compile there    │
  ├─────────────────────────────────────┼───────────────────────────────────┤
  │                                     │ it passes once the agent's fix is │
  │ agent_test_passes_on_fix            │  applied (after the project       │
  │                                     │ builds)                           │
  ├─────────────────────────────────────┼───────────────────────────────────┤
  │ existing_tests_passed               │ the project's other tests still   │
  │                                     │ pass                              │
  ├─────────────────────────────────────┼───────────────────────────────────┤
  │ upstream_test_fails_on_vuln /       │ the upstream oracle, on the       │
  │ _passes_on_fix                      │ vulnerable tree / the agent's fix │
  ├─────────────────────────────────────┼───────────────────────────────────┤
  │                                     │ the agent's test also passes on   │
  │ agent_test_passes_on_upstream_fix   │ the hidden upstream fix — so it   │
  │                                     │ tests the bug, not the agent's    │
  │                                     │ particular patch                  │
  └─────────────────────────────────────┴───────────────────────────────────┘

  base = fix and test apply, build ok, fails before, passes after, existing
  tests not failing. Then:

  ┌──────────┬───────────────────────────────────────────────────────────────┐
  │   Tier   │                          Requirement                          │
  ├──────────┼───────────────────────────────────────────────────────────────┤
  │ T1       │ base + upstream oracle fails on vuln and passes on the        │
  │          │ agent's fix                                                   │
  ├──────────┼───────────────────────────────────────────────────────────────┤
  │ T2       │ base + the agent's test also passes on the hidden upstream    │
  │          │ fix                                                           │
  ├──────────┼───────────────────────────────────────────────────────────────┤
  │ T3       │ base + passes on a known fixed release                        │
  ├──────────┼───────────────────────────────────────────────────────────────┤
  │ T4       │ base only (self-consistent)                                   │
  ├──────────┼───────────────────────────────────────────────────────────────┤
  │ rejected │ anything less                                                 │
  └──────────┴───────────────────────────────────────────────────────────────┘

  No model judges correctness — it's all executable tests and versioned rules.
  The verdict goes to grade_calls.jsonl.

  ---

  Stage 5 — Langfuse (one trace per attempt, reasoning kept)

  The LiteLLM proxy's own logging drops GLM's reasoning and scatters each call
  into its own trace. So after verification the runner posts the episode itself
  from the local transcript (cvepatch/runner/langfuse_sync.py):

  - one trace per CVE attempt, grouped by CVE, tagged tier:, cve:, lang:
  - one generation per turn, with reasoning_content, inputs and token usage
  - one span per tool call (args in, result out)
  - scores: tier (categorical), tier_rank (T1=4 … rejected=0), and every boolean
    check

  GLM's prior reasoning is also replayed to it each turn, so the recorded chain
  is the one the model actually worked from. (I verified this round-trips
  against the real Langfuse.)

  ---

  Stage 6 — Export to training data

  scripts/export_traces.py --min-tier T2 turns the verified runs into JSONL in
  OpenAI chat format — messages with reasoning_content, tool calls, the tool
  surface, and the verdict — filtered by tier. That's the artifact you train on.

  ---

  The guarantees that make the traces worth training on

  1. The answer is hidden. The agent never sees the fix; a leak test enforces
     it.
  2. The test must fail first. A patch that passes a test that never failed
     proves nothing, so agent_test_fails_on_vuln is required.
  3. Cross-check against the real fix. T1/T2 require the agent's work to agree
     with the independent upstream fix, which stops it from writing a test that
     only fits its own patch.
  4. No LLM in the verdict. Only compiled-and-run tests decide the tier.
  5. Deterministic and repeated. Each check runs twice; a flaky result can't
     pass.

  ---

  Where it runs

  k8s namespace exploitbench, one pinned node, Docker-in-Docker pods
  (deploy/kube/). One DinD Job at a time, since they share a persistent image
  store. The two Jobs you start: cvepatch-run.yaml (the agent episode) and
  cvepatch-taskgen.yaml (confirmation). Task generation and triage run on the
  host without Docker.

  If you want, I can draw this as a one-page diagram, or go deeper on any single
  stage — the verifier's tier logic and the bundle split are the two places
  most of the subtlety lives.
